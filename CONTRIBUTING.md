# Contributing

Thanks for helping. A few rules keep the project small and trustworthy.

- **Open an issue first** for anything bigger than a fix, so the design is
  agreed before the code.
- **Before you push:** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
  `cargo test`, `python3 scripts/leak_check.py` and `python3 scripts/docs_check.py`.
  CI runs the same, plus
  `cargo deny`, zizmor over the workflows and `dist generate --check`.
- **Workflows:** pin every action by commit SHA. `release.yml` is generated by
  `dist generate`; never edit it by hand. When Dependabot bumps an action that
  `release.yml` uses, update `[dist.github-action-commits]` in
  `dist-workspace.toml` to the same SHA and regenerate, or the `dist` job fails.
- **Tests:** anything with a branch, a loop or a rule gets a test. Integration
  tests drive the built binary (`tests/`).
- **A faster edit loop (optional):** [blaze](https://github.com/indexable-inc/ra-jit)
  (still published as `ra-jit`) keeps the workspace loaded in a daemon and
  rebuilds only what an edit touched. On Linux x86_64, rebuilding and running
  the binary after an edit took 0.1 s instead of 2 s in the `fairlead` crate,
  and 0.1 s instead of 5 s in `fairlead-core`; the first build loads the
  workspace and takes about a minute. It needs Rust 1.99.0, newer than the
  pinned toolchain, so name it on each command:
  `rustup toolchain install 1.99.0 -c rust-src`,
  `cargo +1.99.0 install --locked ra-jit`, then
  `cargo +1.99.0 ra-jit build`, `run` or `test`. It runs no borrow checker,
  so `cargo check` and `cargo clippy` stay the judge, and it falls back to
  cargo for what it can't build (`cargo ra-jit status` says what). Linux and
  Apple silicon only. CI and releases build with cargo.
- **No project-specific logic.** Fairlead must work in any repository, so
  issues, pull requests and commit messages stay generic too (the `leak-text`
  workflow checks them).
  Anything specific to one project belongs in that project's `fairlead.toml`,
  never here. Fixtures are synthetic.
- **Docs follow the code.** A change that adds or changes what a user can do
  updates the README, `site/index.html` and the book in the same PR. A feature
  is labelled with the release it shipped in (`*Since 0.6.0:*`), or
  `*Unreleased:*` until it has one; a promise names a roadmap milestone
  (`*Coming in K4*`), and the roadmap's Status column says what has shipped.
  `scripts/docs_check.py` fails on a page that lags.
- **Releasing:** one PR bumps every crate's version and the exact
  `version = "=X.Y.Z"` pins between the `fairlead-*` crates, dates the `Unreleased`
  notes as the new version, and moves each `documents Fairlead X.Y.Z` line,
  `*Unreleased:*` label, the README's Status, the action pin in
  `docs/src/ci.md` and the Composer launcher's `STAMPED` version in
  `src-php/Version.php` to it. The Status describes that release alone and points
  to the changelog for the rest, and the release's section goes at the end of
  the upgrade guide (`docs/src/migrate.md`), whose releases run oldest first;
  `scripts/docs_check.py` fails on either. Before tagging,
  `python3 scripts/docs_check.py --release vX.Y.Z` must pass on the merged
  main. The tag goes on that commit.
  `release.yml` runs the same check before it builds anything, so a tag the
  docs lag builds nothing, releases nothing and publishes nothing.
  After the approval, the release publishes to npm, crates.io (the six crates,
  dependencies first, skipping any version already there, so a re-run is safe)
  and the Homebrew tap.
- **Publishing setup, once, by the owner,** while the first release that
  publishes to crates.io and Homebrew waits for its approval:
  1. From the tagged commit, `cargo publish` each crate by hand in dependency
     order (`fairlead-core`, `fairlead-lang`, `fairlead-tests`,
     `fairlead-guard`, `fairlead-replay`, `fairlead`) with a short-lived
     crates.io token scoped to publishing new crates. crates.io sets up
     trusted publishing only for a crate that exists.
  2. On crates.io, give each of the six crates a trusted publisher: this
     repository, workflow `release.yml`, environment `release`.
  3. Revoke the token.
  4. Create the `mahkassem/homebrew-tap` repository with a first commit (a
     README), so it has a default branch to push to.
  5. Mint a fine-grained token with Contents read and write on that repository
     only, and store it as the `HOMEBREW_TAP_TOKEN` secret of the `release`
     environment, not as a repository secret.
  6. Approve the release. Its crates.io job finds the six versions already
     published and skips them, so the next release is the first that
     publishes through the trusted publishers.
- **Dependencies:** say why in the PR. Every new crate must pass `cargo deny`.
- **Commits** follow Conventional Commits in the imperative mood.
